01

예약이 성공한 다음, 어떤 데이터를 믿을 것인가

예약 생성에 성공하면 응답의 ID로 상세 화면에 이동합니다. 하지만 응답에는 최신 포인트 잔액이나 완전한 예약 상세 객체가 보장되지 않았습니다. 부분 응답을 완전한 데이터처럼 캐시에 넣으면 서버가 주지 않은 값을 추측하게 됩니다.

02

응답과 화면 이동에 맞춘 캐시 선택

예약 상세 캐시를 직접 만들지 않고 포인트 잔액을 무효화해 다시 조회했습니다. 같은 화면에 완전한 최신 객체가 있으면 setQueryData, 부분 응답·화면 이동·집계 변화에는 invalidateQueries를 고려하도록 기준을 문서와 API 연동 스킬에 반영했습니다.

03

버튼 비활성화보다 먼저 들어오는 두 번째 클릭

회귀 테스트에서 대기 없이 확인 버튼을 두 번 누르면 예약 생성 함수가 두 번 호출됐습니다. mutation.isPending은 재렌더 뒤에 바뀌므로 두 handler가 이전 값을 읽을 수 있었습니다. handler 진입 시 useRef 잠금을 잡고 요청 종료 시 해제하도록 수정했습니다.

04

검증과 한계

당시 PR 테스트는 연속 클릭 시 한 번 호출되는 것, 실패 후 재시도, 요청 중 취소·Escape 닫기 제한을 확인했습니다. 검증 범위는 클라이언트 동작이며, 서버의 중복 처리 보장과는 별개입니다.
