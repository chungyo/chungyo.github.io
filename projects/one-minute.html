01

배경: 하나의 서비스, 네 곳의 구현

마음모음 1minute은 웹·앱·관리자·서버가 함께 동작하는 멘탈 웰니스 서비스입니다. 고객이 설명하는 하나의 기능이 여러 구현과 디자인·에셋에 걸쳐 있을 수 있어, 요구사항과 각 구현의 차이를 확인하는 PM 업무를 맡았습니다.

프론트엔드 개발도 함께 수행하며 고객 자료에 적힌 조건이 실제 응답과 화면 흐름에서 어떤 의미인지 대조했습니다.

02

문제: 모든 요청을 새 개발로 계산할 수는 없다

계약 항목과 고객 요구를 다시 확인하면서 신규 기능인지, 기존에 포함됐지만 개발 차수가 이동한 항목인지 구분했습니다. 또한 디자인·에셋이 없는 UI 작업은 착수에 필요한 조건부터 정리해야 했습니다.

범위를 판단할 때 대조한 기준
확인 대상질문연결할 산출물
고객 원문·계약 항목처음 합의한 범위에 포함됐는가?범위 해석
웹·앱·관리자·서버 구현어디까지 구현돼 있고 무엇이 다른가?채널별 작업
디자인·에셋화면 개발을 시작할 입력이 있는가?착수 조건
개발 차수새 요구인가, 기존 작업의 이동인가?차수별 개발 범위
03

판단과 결과: 11건 중 6건은 차수 이동

계약 항목 11건 중 6건을 신규 요구가 아닌 개발 차수 이동으로 판정해 범위에 반영했습니다. 같은 요청을 다시 신규 기능으로 계산하지 않도록 원문과 구현 상태를 함께 본 결과입니다.

이 숫자는 범위 분류 결과입니다. 전체 작업량 6건을 없앴다거나 개발비를 그 비율만큼 줄였다는 의미가 아닙니다.

범위 판단의 단위

항목 수, 구현 완료, QA 통과, 앱 출시 여부는 각각 다른 상태로 관리합니다. 분류가 끝났다고 해당 기능의 배포까지 끝난 것은 아닙니다.

04

개발 전달: 알림 하나에도 필요한 조건

알림 기능은 ‘발송한다’는 문장만으로 개발과 검증을 끝낼 수 없었습니다. 동의 여부·발송 시점·실패·딥링크 정책을 정리해 FE·BE·앱·관리자 작업과 인수 기준으로 전달했습니다.

이 도식은 정리한 정책의 연결 관계이며 특정 발송 성공률이나 모든 기기에서의 동작 완료를 뜻하지 않습니다.

05

기술 구현: WebView 경계의 응답 정규화

React Native와 WebView 사이의 구독 응답은 화면에서 처리할 payload와 error를 정규화했습니다. 거래 식별자를 기준으로 중복 검증 요청을 차단하고 검증 실패 시에는 잠금을 해제해 재시도할 수 있도록 구현했습니다.

구독 응답에서 구분한 동작
상황처리지켜야 할 점
네이티브 응답 수신payload·error 정규화화면이 응답 형태를 일관되게 해석
같은 거래 응답 반복거래 ID·토큰 기준 중복 차단검증 요청의 중복 실행 방지
검증 실패재시도 가능하도록 잠금 해제한 번의 실패가 영구 차단으로 남지 않음
06

검증과 한계

확인한 기여와 별도 확인 대상
영역확인된 내용확대하지 않은 주장
요구사항·범위원문·구현 대조와 차수 분류공수·비용 절감률
알림정책·역할별 작업·인수 기준 정리모든 발송·기기 검증 완료
구독 응답정규화·중복 차단·실패 후 해제 코드결제 플랫폼 전체의 중복 보장
사용 규모이 사례에서 유효한 성과 지표 미확인분석 방문자를 가입·유료 고객으로 변환

구독 응답의 프론트엔드 수정과 서비스 전체의 출시 상태는 분리해서 설명합니다. 코드 대조 기록은 있지만 이번 편집에서 네이티브 기기나 운영 결제를 새로 테스트하지 않았습니다.

07

돌아보며: 범위와 예외를 같은 문장으로 전달하기

PM 작업에서는 원문과 구현을 대조해 무엇을 어느 차수에 만들지 정리했고, 구독 응답 구현에서는 성공·중복·실패를 나누어 처리했습니다. 둘 다 일반적인 정상 흐름만으로 작업 완료를 판단하지 않는 접근이었습니다.

이 사례는 기능 목록 자체보다, 고객이 요청한 조건을 여러 팀의 구현과 재시도·검증 기준까지 연결한 경험으로 설명할 수 있습니다.
