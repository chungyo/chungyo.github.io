01

배경: 정상적인 업데이트 사이에 숨어 있는 경계 조건

Toss react-simplikit에서 저장소 이벤트와 React ref/effect 실행 순서에 관한 두 오류를 수정했습니다. 공개 함수의 사용 방법을 바꾸기보다 기존 동작이 지켜져야 할 조건을 재현하고 회귀 테스트로 남긴 기여입니다.

두 PR은 각각 useStorageState와 useRefEffect를 다룹니다. 같은 저장소의 기여이지만 서로 다른 오류이므로 재현·원인·수정·검증도 구분해 설명합니다.

02

사례 1 — 재현: 다른 탭에서 전체 삭제한 뒤에도 이전 값

기본값이 Guest라면 저장소 전체 삭제 후에는 Guest를 보여줘야 하는 상황이었습니다. 하지만 전체 삭제 이벤트를 기존 구독 조건이 놓치고 있었습니다.

03

사례 1 — 원인과 선택: null 이벤트도 snapshot을 다시 읽기

전체 삭제 이벤트의 key는 null인데 기존 코드는 관찰하는 key와 일치하는 이벤트만 처리했습니다. null인 경우에도 구독자를 깨워 기존 snapshot 로직이 저장소를 다시 읽도록 조건을 수정했습니다.

수정의 범위
항목기존 문제수정 기준
관찰 key 변경해당 key 이벤트 처리기존 의미 유지
전체 삭제key=null이라 처리 누락구독자에게 변경 알림
반영 값이벤트 newValue를 곧바로 적용할 위험훅이 사용하는 저장소의 snapshot 재조회
다른 저장소의 삭제현재 저장소와 구분 필요현재 저장소 값이 잘못 초기화되지 않도록 검증

단순히 null 이벤트를 받으면 기본값으로 바꾸는 접근은 선택하지 않았습니다. 현재 훅이 읽는 저장소에 어떤 값이 있는지 다시 확인하는 기존 흐름을 유지했습니다.

04

사례 2 — 재현: 새 의존성인데 이전 setup이 실행

useRefEffect의 의존성이 A에서 B로 바뀌면 cleanup(A) 다음에 setup(B)가 실행돼야 했습니다. 그러나 ref 부착이 effect보다 먼저 실행되면서 이전 콜백을 읽어 setup(A)가 다시 호출되는 문제가 있었습니다.

의존성 변경 시 순서
단계기대 동작재현된 문제
이전 연결 정리cleanup(A)이전 연결 정리
새 ref 부착새 의존성의 콜백 사용effect 갱신 전 이전 콜백 읽음
새 연결 설정setup(B)setup(A)가 다시 실행
영향받는 소비 훅새 observer 옵션 적용이전 observer에 요소를 연결

이 흐름은 useIntersectionObserver에도 이어져 observer 옵션을 바꿨을 때 이전 observer에 요소를 붙이는 문제로 나타났습니다.

05

사례 2 — 구현: 의존성이 바뀔 때 새 콜백 보관 객체

의존성이 바뀌면 콜백을 담는 객체를 새로 만들도록 수정했습니다. 의존성이 같을 때는 effect에서 콜백을 갱신하는 기존 의미를 유지했습니다.

렌더 도중 기존 객체를 덮어쓰지 않는 것도 중요했습니다. 커밋되지 않은 렌더에서 만든 콜백이 현재 동작에 섞이지 않도록, 의존성별 보관 구조로 구분했습니다.

변경 범위

공개 함수 시그니처와 공통 usePreservedCallback은 유지했습니다. 공통 훅을 광범위하게 바꾸는 대신 문제가 있는 수명주기의 범위를 수정했습니다.

07

결과와 이후 확인할 범위

useStorageState #482는 2026년 9월 8일, useRefEffect #483은 9월 9일 병합됐습니다. 공개 PR에서 수정·리뷰·병합 이력을 확인할 수 있습니다.

병합과 패키지 릴리즈 포함은 다른 상태입니다. 다운로드 수를 곧바로 영향 사용자 수로 계산하거나, 전체 소비 서비스의 오류 감소를 제 성과로 주장하지 않습니다.

08

돌아보며: 조건과 순서를 테스트 이름으로 남기기

첫 오류는 어떤 이벤트를 받는지, 두 번째는 콜백 갱신과 ref 부착 중 무엇이 먼저인지가 원인이었습니다. 일반적인 업데이트만 확인하면 놓칠 수 있는 조건을 실제 재현으로 좁히고 테스트에 남겼습니다.

리뷰 과정에서는 테스트의 양보다 보호하려는 동작이 분명한지도 확인했습니다. 수정 범위를 설명하는 것과 같은 수준으로 회귀 조건을 설명할 수 있어야 했습니다.
